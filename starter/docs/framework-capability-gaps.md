# Framework capability gaps

Research dated 2026-09-25. Recommendations below are proposed work, not implemented capabilities. Comparison uses official Laravel 13.x and Django 5.2 documentation; it does not claim framework parity or production verification.

Implementation follow-up, 2026-09-25: the first two recommendations now have [developer tooling](features/tooling.md): `doctor`, `inspect --json` and opt-in read-only migration history. The table below preserves the original research baseline. Scaffolding, prior-release upgrade automation, shared integration-test tooling and admin remain proposed work. See [verification](verification.md) for executed checks.

The largest opportunity is executable developer assistance: commands that let humans and agents inspect, validate, and extend the application consistently. The [catalog](features/index.md) already covers most common application services as recipes. Adding more libraries is less useful than turning selected conventions into observable behavior.

| Priority | Capability and framework precedent | Present here | Smallest useful addition and AI benefit |
| --- | --- | --- | --- |
| 1 | Deployment/system checks. Django provides tagged checks, stable diagnostic identifiers, and additional deployment checks through [`check --deploy`](https://docs.djangoproject.com/en/5.2/ref/django-admin/#check) and its [check framework](https://docs.djangoproject.com/en/5.2/ref/checks/). | Configuration parsing, readiness, CI checks and operational guidance exist; there is no independent diagnostic command. See [config](../src/config.rs), [quality](quality.md), and [operations](operations.md). | A read-only `doctor --json`, with stable codes, severity, explanations and remediation. Reuse existing config validation, detect opted-in example routes in deployment mode, and optionally check connectivity and pending migrations. Clearly identify checks that require external deployment evidence. Agents get actionable failures instead of guessing from a generic startup error. |
| 2 | Application inspection. Laravel provides [`route:list` with middleware details](https://laravel.com/framework/docs/13.x/routing#listing-your-routes); [Boost](https://laravel.com/framework/docs/13.x/boost#mcp-server) exposes application/package information, schema inspection and package-aware documentation search to agents. | Generated [OpenAPI](http.md), the capability catalog, lockfile and source already expose substantial context, but not one executable inventory. The [main CLI](../src/main.rs) offers only `serve` and `migrate`. | A small read-only `inspect --json` showing versions, commands, enabled capabilities, effective route availability, migration state and links to local recipes. Reuse OpenAPI instead of duplicating it; it currently describes opt-in routes even when disabled. Redact secrets and keep optional database inspection separate. MCP can wrap this later if a real consumer needs it. |
| 3 | Feature generators. Laravel's [Artisan stubs](https://laravel.com/framework/docs/13.x/artisan#stub-customization) generate controllers, jobs, migrations and tests using customizable templates. | [README](../README.md) instructs developers to replace the notes slice manually; no generator or generator recipe exists. | A reviewed `make feature` template based on notes: module/entity, migration stub, route/OpenAPI wiring and success/failure test skeletons. Preview changes, refuse overwrites and require explicit access-control decisions. This reduces forgotten wiring and repeated agent invention; generated skeletons still need domain decisions and real verification. |
| 4 | Migration visibility and preflight. Django offers [`showmigrations`, `sqlmigrate`, `migrate --plan` and pending-migration checks](https://docs.djangoproject.com/en/5.2/ref/django-admin/); Laravel offers [`migrate --pretend`](https://laravel.com/framework/docs/13.x/migrations#running-migrations). | Forward migration and disposable up/down tests exist. Expand/backfill/contract, prior-release fixtures, lock timeouts and serialized deployment are already documented in [operations](operations.md), but not automated. | First add a read-only applied/pending list and an executable previous-release upgrade test. Then expose reviewed SQL where possible and validate migration serialization/timeouts. Arbitrary Rust migration code cannot be promised a harmless general-purpose dry run; a plan must disclose its limits. Agents gain a reviewable change boundary before mutation. |
| 5 | Reusable test scenarios and side-effect controls. Laravel [factory states](https://laravel.com/framework/docs/13.x/eloquent-factories#factory-states) construct named scenarios; its HTTP client can [reject requests without configured fakes](https://laravel.com/framework/docs/13.x/http-client#preventing-stray-requests). | PostgreSQL schema isolation is implemented in [tests/http.rs](../tests/http.rs). Fixture builders/seeds are prescribed in [data](features/data.md); clocks and local stub testing appear in other recipes. There is no shared scenario/fake toolkit. | Extract test support when a second feature needs it. Add named tenant/role scenarios with identity, and fail unexpected external calls when providers are introduced. Provide controlled clocks for expiry/retry tests. Agents can reproduce denial, duplicate-delivery and timeout paths without fragile sleeps or accidental provider calls. |
| 6 | Internal administration. Django's [model-driven admin](https://docs.djangoproject.com/en/5.2/ref/contrib/admin/) is intended for trusted internal management. | No admin capability/recipe. Administrator authorization and failed-job replay are mentioned in [identity](features/identity.md) and [jobs](features/jobs.md). | Document an optional operations UI/CLI recipe first: resource lookup, narrowly authorized actions, audit reasons and safe job replay. Implement after identity and real support workflows exist. Useful for humans inspecting AI-produced workflows, but less valuable than the first five for this small API starter. |

Recommended order: diagnostic and inspection commands, a checked feature template, migration preflight, then shared testing support as integrations arrive. Keep admin optional. Authentication, jobs, email, storage and scheduling are already documented choices; their absence at runtime should not be mistaken for missing documentation.

Evidence: read README, catalog, HTTP/database/operations/quality guidance, relevant recipes, `src/main.rs`, `src/config.rs`, `src/migrations/mod.rs`, `scripts/dev.sh` and test references; searched `docs`, `src`, `scripts` and `tests` with `rg`; opened the cited official framework pages. This is a documentation-only comparison. No runtime feature was added and no application, database, or container test was run for this report.
