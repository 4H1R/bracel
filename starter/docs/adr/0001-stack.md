# Explicit Axum application with SeaORM and PostgreSQL

Accepted 2026-09-25. Distribution updated 2026-09-26: reusable infrastructure now ships as Bracel with a separate starter. The original single-crate rule below now applies to the application. Use a single Rust application crate, Axum 0.8.9, SeaORM and sea-orm-migration 2.0.3, PostgreSQL 18, and utoipa 6.0.0. The compiler is pinned to Rust 1.98.1; the complete resolved dependency set is in `Cargo.lock`. This buys a small runtime with explicit seams and requires us to own HTTP errors, configuration, and extension instructions.

Loco was evaluated first. Its [CLI reference](https://loco.rs/docs/reference/cli/) and [first application tutorial](https://loco.rs/docs/tutorials/your-first-app/) describe a lightweight controller-only starter and a database starter with authentication. We inspected the actual generator inputs at commit `9f7e021e9fe68275a9a7e1ab3e7dd25c483d2bd8`: [manifest](https://github.com/loco-rs/loco/blob/9f7e021e9fe68275a9a7e1ab3e7dd25c483d2bd8/loco-new/base_template/Cargo.toml.t), [configuration](https://github.com/loco-rs/loco/blob/9f7e021e9fe68275a9a7e1ab3e7dd25c483d2bd8/loco-new/base_template/config/development.yaml.t), and [wizard](https://github.com/loco-rs/loco/blob/9f7e021e9fe68275a9a7e1ab3e7dd25c483d2bd8/loco-new/src/wizard.rs). Database output includes a second migration crate, both SQL drivers, user authentication, and mailer conventions. These are useful for an integrated application, but removing or adding back these pieces would dominate this deliberately minimal starter. No Loco runtime is retained. Source/template inspection is not a claim that a generated Loco application was executed.

The selected approach has feature modules (`notes`) and small shared infrastructure; handlers call concrete application functions which use SeaORM directly. [The organization decision](0002-feature-modules-and-http-contracts.md) specifies feature interfaces and shared HTTP contracts. Introduce an interface at an actual external integration boundary, not a generic repository layer. Migrations stay in the application crate. The example can be disabled or enabled; the later [middleware extension](../middleware.md) adds anonymous teaching and bearer-authenticated runtime modes. No optional Cargo feature matrix exists yet.

Generated output was also inspected in Loco's checked-in [PostgreSQL manifest snapshot](https://github.com/loco-rs/loco/blob/9f7e021e9fe68275a9a7e1ab3e7dd25c483d2bd8/loco-new/tests/templates/snapshots/r%23mod__templates__db__cargo_dependencies_Postgres.snap) and [auth-enabled application snapshot](https://github.com/loco-rs/loco/blob/9f7e021e9fe68275a9a7e1ab3e7dd25c483d2bd8/loco-new/tests/templates/snapshots/r%23mod__templates__auth__src_app_rs_auth_true_Sqlite.snap). These confirm the generated dependencies and auth route/user task wiring; we did not run the Loco app or treat the SQLite snapshot as PostgreSQL runtime evidence.

Official version/API sources checked during authoring: [Rust stable distribution manifest](https://static.rust-lang.org/dist/channel-rust-stable.toml), [Axum](https://docs.rs/axum/0.8.9/axum/), [SeaORM](https://docs.rs/sea-orm/2.0.3/sea_orm/), [migrations](https://docs.rs/sea-orm-migration/2.0.3/sea_orm_migration/), [utoipa](https://docs.rs/utoipa/6.0.0/utoipa/), [PostgreSQL 18](https://www.postgresql.org/docs/18/). Manifests allow compatible updates; builds use the lockfile. SeaORM's migration/schema crates still pull shared SQL/type utilities transitively; only the PostgreSQL driver is enabled, and no Redis, SMTP, cloud SDK, or identity provider is used by the core. See [verification](../verification.md) for executed results.
