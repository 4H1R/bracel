# Authentication, authorization, and tenant isolation

## Implemented bearer access tokens

Implemented 2026-09-25 for machine/mobile API callers. `bracel::identity` validates issuer-signed JWT access tokens using jsonwebtoken 11.1.0 with the aws-lc-rs backend. `bracel::http::middleware` handles Authorization parsing and scope enforcement; [middleware](../middleware.md) describes route composition. Browser OIDC login, sessions, ownership and tenant isolation below remain recipes.

Set `AUTH_MODE=bearer`, `AUTH_PUBLIC_KEY_PEM` to the issuer's RSA public PEM, `AUTH_ISSUER` to the exact issuer claim, and `AUTH_AUDIENCE` to this API's audience. Missing/invalid settings fail configuration, without echoing values. Key material is parsed at startup. `AUTH_MODE=off` is the local teaching default and rejects leftover auth settings instead of silently ignoring them. Real private route groups must always use `Access::Scope`; that policy fails closed if no verifier exists. Deployment doctor still rejects teaching routes even with authentication enabled.

The verifier pins RS256, requires `typ=at+jwt`, validates signature, exact issuer, audience membership, required expiry and nonempty subject, and validates nbf when present with zero clock-skew allowance. Tokens are bounded to 8192 bytes. Unsupported critical headers are rejected, and token-supplied key URLs are never fetched. Claims use a space-separated `scope` string. Notes reads need `notes:read`; creates need `notes:write`. Missing, expired, malformed, wrongly signed or incompatible tokens receive 401/WWW-Authenticate; missing scope receives 403. Errors never include token or parser details. Protected successful responses use Cache-Control: no-store.

Configure the provider to issue short-lived access tokens with that audience/type/scope contract. ID tokens, refresh tokens, opaque tokens and HS256 are not accepted. This application does not issue tokens or implement a mobile login flow. Obtain access tokens through the provider's supported flow. The public key is supplied out of band; automatic JWKS discovery/rotation and immediate revocation are not implemented. Coordinate key changes with rolling restart/token lifetimes; if overlap or immediate revocation is required, implement a key-set/introspection contract before depending on it. Scope removal takes effect when an old token expires. The public key alone cannot mint tokens. Never configure the checked-in test-only fixture key in a running deployment.

`Principal` identifies issuer/subject and scopes; it is not a database user or tenant membership. Notes remains a deliberately shared collection for scope-authorized callers, with cursors bound to issuer/subject. Add owner/tenant predicates in application operations before treating it as private per-user storage. Background callers must receive verified authorization context too. No cookie credentials are accepted, so cookie CSRF middleware is not applicable. The browser-session recipe below requires CSRF/Origin enforcement if implemented.

Tests cover valid access, missing/invalid claims, expiry/nbf, algorithm rejection, scope denial, duplicate Authorization, cross-principal cursor rejection, CORS preflight and safe 401/403 responses. This is local JWT verification evidence, not an exercised third-party issuer integration. Source: [jsonwebtoken validation](https://docs.rs/jsonwebtoken/11.1.0/jsonwebtoken/struct.Validation.html).

## When and what to choose

Use this when a real client accesses private resources. The local teaching API needs no identity, but must be replaced or protected before public use. First decide: same-site browser, cross-origin SPA/mobile, or machine API? For a first-party browser recommend OIDC authorization-code + PKCE, an external identity provider, and opaque PostgreSQL sessions. This delegates password reset/MFA/email verification to the provider and avoids a password database in this starter. For bearer-token APIs, select the issuer's access-token validation or introspection contract explicitly; ID tokens are not API access tokens.

Authoring check 2026-09-25: [openidconnect 4.0.1](https://docs.rs/openidconnect/4.0.1/openidconnect/) (`4.0` constraint), its reqwest integration uses the `0.12` line. Keep that client version compatible even if unrelated outbound APIs use newer reqwest. Follow the [OIDC code flow](https://openid.net/specs/openid-connect-core-1_0.html#CodeFlowAuth). **Documentation-only; no authentication code was compiled or executed.** Recheck advisories and compatibility during implementation.

## Smallest complete implementation

1. Add openidconnect with async HTTP support and the compatible HTTP client, a cookie parser, and cryptographic random/hash helpers. Check their lockfile and cargo-deny results. Create a validated identity configuration with issuer URL, client ID/secret, exact redirect URI, and allowed origin. Require it only when identity is enabled; keep secrets out of Debug/logs.
2. Add migrations for users keyed by unique `(issuer, subject)`, one-use login attempts (hashed state, nonce/PKCE verifier, expiry), and sessions (hashed random token, user ID, expiry/revocation). Use at least 32 random bytes per session token. Store only its cryptographic hash; never put provider tokens or roles in a client-readable cookie. Put the OIDC client in `AppState`, discovered at startup with bounded network timeouts and HTTPS issuer validation.
3. Add login/callback/logout routes. Validate state, nonce, signature, issuer, audience, expiry and PKCE; consume login state atomically once. Regenerate the session on login/privilege change. Set `__Host-session` with Secure, HttpOnly, Path=/, SameSite=Lax and no Domain in HTTPS environments. Local HTTP requires an explicitly separate development cookie policy. Reject untrusted return URLs. Add CSRF token and exact Origin checks for unsafe cookie-authenticated methods. Logout revokes server state and clears the cookie.
4. Add a `Principal` extractor that loads the session and current memberships, failing with safe 401 problem details. Use it in the replacement notes routes. Add a nullable owner column, backfill or discard example data deliberately, then enforce NOT NULL. Filter **every read and write** by owner/tenant in the database query, so another user's ID returns 404. Authentication alone grants no resource permission. Add named policy functions for administrator operations; test both allowed and denied cases.
5. For tenants, add tenants and memberships, select an active tenant only after checking membership, and scope all keys/queries/jobs/cache entries to that tenant. Composite foreign keys prevent cross-tenant references. Consider PostgreSQL RLS as defense in depth only with a carefully tested transaction-local tenant context and non-bypass role; a pooled connection must never leak tenant state. This is a project decision, not enabled by the starter.
6. Delegate reset and verification screens to the issuer; require a verified email claim only if the product needs it. Email is not the stable account key. If local passwords are required instead, make a new decision covering Argon2id parameters, breached-password rules, enumeration-resistant responses, short-lived hashed single-use reset tokens, verification, abuse limits, and [durable email](email.md).

## Failure, verification, and operations

Bound discovery/token requests (2-second connect, 5-second total); disable redirects. Do not retry a consumed authorization code blindly. Cache keys with refresh/backoff, reject unknown issuers/algorithms, and fail closed on ambiguous authorization. Provider downtime should prevent new logins, not invalidate locally valid sessions unnecessarily. Never log tokens, codes, cookies, reset links, or raw claims.

Run `cargo test --locked --test identity` after creating it, then `bash scripts/check.sh` and `bash scripts/container-smoke.sh`. Acceptance cases: successful login/session rotation, expired/forged/replayed state and token, wrong nonce/issuer/audience, expired/revoked session, CSRF/mismatched Origin, logout, cross-user and cross-tenant note IDs, role removal, key rotation, and issuer outage. If role delegation is supported, verify the target belongs to the authorized tenant and granted permissions are a subset of the actor's delegable permissions. Serialize complete responses with nested user associations and assert that only explicit public DTO fields appear; password hashes, reset/session tokens and private account fields must stay absent at every nesting level. CI should run the local issuer fixture, with tests requiring its URL rather than silently skipping. Update `ApiDoc` security schemes/responses and regenerate the spec.

Deploy callback URLs and secret references per environment; rotate keys/credentials and clean expired sessions in bounded batches using [scheduling](scheduling.md). Count login failures by safe category, never identity. Readiness should represent resources needed to serve existing sessions; expose issuer outage separately. Roll back application changes only with compatible session/schema formats; revoke sessions after a signing/credential compromise. Record executed evidence before marking this recipe implemented.

## Durable audit history, when required

When the product needs an authoritative history of permission changes or other sensitive mutations, create `src/features/audit/mod.rs` and append an audit-table migration to `src/migrations/mod.rs`. Record an allowlisted action, actor, target resource, target tenant, timestamp and safe metadata. Attribute the event to the resource's tenant after authorization; a platform operator's home tenant must not override that attribution. Keep secrets and unrestricted request bodies out of audit payloads.

Pass the same `ConnectionTrait` transaction to the mutation and audit insert. Commit only when both succeed; an audit storage failure rolls the mutation back. This uses the composition pattern already demonstrated by `notes::create_note`. Denied actions have no successful mutation to commit alongside: record them separately under an explicit best-effort policy, count capture failures, and retain the original denial response. Give audit data its own access, retention and tamper-resistance policy. Ordinary tracing logs may be sampled or dropped and are not a durable audit history.

Add PostgreSQL tests for successful mutation plus one audit row, audit-insert failure rolling back the mutation, mutation failure leaving no success audit, denial capture failure preserving the denial, and correct target-tenant attribution. These audit and authorization refinements were informed by [the Zoora comparison](../zoora-review.md); they remain documentation-only until identity/audit is requested. Do not add an audit table to the starter by default.
