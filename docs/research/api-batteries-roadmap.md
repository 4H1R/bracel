# API-only batteries roadmap

Research and source inspection: 2026-09-26. This is a proposal, not implemented behavior or new runtime verification. The input is the user's Laravel/Django/Rails feature inventory. Bracel remains API-only: JSON, files, streaming and realtime protocols; no page rendering, frontend assets, forms UI or admin dashboard. All work stays local until publishing is explicitly authorized.

## What already exists

The [capability catalog](../../starter/docs/features/index.md) and [batteries guide](../../starter/docs/batteries.md) describe a substantial baseline: Axum HTTP, shared success/error contracts, OpenAPI/route registration, validation extractors, allowlisted queries, forward keyset pagination, JWT verification/key rotation, revocable machine tokens, record policies, local quotas, SeaORM/PostgreSQL migrations, transactional job enqueueing, leased workers, interval schedules, CRUD generation, commands, diagnostics and optional mail/storage/cache/outbound HTTP/OTLP adapters.

The important gap is complete workflows across these modules. Installing a mail adapter is not queued notification delivery; an object-store adapter is not an authorized attachment lifecycle. SeaORM already supplies relationships, transactions and SQL capabilities: missing Bracel conventions should not be confused with a missing ORM.

## Recommended additions, in dependency order

| Area | Current implementation / gap | Proposed next behavior |
| --- | --- | --- |
| Validation and resource generation | [Fields](../../crates/bracel/src/http/fields.rs) supplies required text, integer and boolean rules; generated fields are string/i64/bool | Optional versus nullable versus omitted fields, nested objects/arrays and issue paths, enums, UUID/date/decimal types, numeric bounds, cross-field rules and PATCH semantics. Keep database uniqueness enforced by constraints with safe conflict mapping. Reuse request metadata for OpenAPI and generation. |
| Resource querying | [QuerySpec](../../crates/bracel/src/query.rs) supports UUID/text/date predicates and declared stable orders; pagination is forward-only | Boolean/numeric/enum filters, bounded lists/ranges, explicitly allowed relationship includes with eager loading, safe response-field selection, backward cursors. Add bounded offset/count pagination only as an explicit alternative for clients needing page numbers. Preserve mandatory access predicates and prohibit unrestricted SQL expressions. |
| Safe mutations | Transactions exist; reusable HTTP idempotency and optimistic version checks do not | Durable, principal/operation-scoped idempotency records with request fingerprints, conflict handling, bounded retention and safe response replay. Couple successful mutation/result persistence in one transaction. For external effects, enqueue intent and use provider idempotency/reconciliation. Add version-based updates, or ETag/If-Match with HTTP precondition semantics. These are additional API priorities beyond the research's feature inventory. |
| Identity onboarding | [BearerAuth](../../crates/bracel/src/identity.rs) verifies configured RSA JWTs; opaque tokens have expiry/revocation. No account lifecycle or remote key discovery | First supply a configured-issuer OIDC/JWKS adapter with bounded refresh, cache/outage rules and documented access-token compatibility; retain strict issuer/audience/algorithm checks. Add an identity-provider starter recipe that actually runs. Registration, reset, verification, MFA/passkeys can remain provider-managed. A self-hosted JSON account module is a separate optional undertaking, including hashing, one-use tokens, refresh rotation/reuse detection and throttling. API-only does not imply machine-only users. |
| Events and delivery | [jobs::enqueue](../../crates/bracel-jobs/src/lib.rs) can share a business transaction; there is no typed event bus or retained broadcast log | Typed, versioned event payloads and explicit transaction-aware publication. Add independent consumer delivery state and retained stream positions; reuse the existing queue for work. A job queue distributes work, whereas a broadcast must reach every entitled subscriber. Keep delivery at least once and deduplicate by event ID. |
| SSE and WebSockets | [Realtime recipe](../../starter/docs/features/realtime.md) only | Rust-native SSE first, authenticated topics, replay, retention-gap recovery, bounded subscriber queues, expiry/revocation, connection quotas and draining. Optional WebSockets share authorization and event envelopes and add validated inbound messages, frame bounds, heartbeat/idle rules and per-message policies. See [realtime research](realtime.md). |
| Notifications and mail workflows | [Mailer](../../crates/bracel-integrations/src/mail.rs) supplies SMTP/capture and message construction | A notification module combining database inbox/read state, queued email and realtime delivery. Persist per-channel attempts, preferences and delivery state. Add mail template/attachment conventions and provider feedback hooks. HTML email formatting does not require a web template engine. |
| Files and attachments | [Storage](../../crates/bracel-integrations/src/storage.rs) supplies bounded scoped object operations; no metadata/upload routes | Explicit pending/available/deleted states, optional quarantine, owner-checked initialization/completion/download/delete, direct-upload capabilities, size/type/checksum verification, attachment references and abandoned-upload cleanup. Keep storage/database reconciliation retryable; they cannot commit atomically together. |
| Webhooks | Documentation only | Outgoing signed delivery with persistent attempts, backoff, delivery IDs and manual replay; incoming raw-body signature verification, timestamp policy and deduplication. Validate destinations before delivery, including private-network/DNS risks. The existing outbound adapter only supports administrator-configured origins, so do not present it as safe arbitrary-URL delivery. |
| Jobs and scheduling depth | PostgreSQL retries/leases, failed-job replay and coalesced intervals exist; handlers accept JSON Value | A typed Job interface and generator, delayed dispatch, named queues, bounded concurrency and configurable attempt deadlines; leases renewed/fenced where long tasks warrant it. Add calendar schedules with explicit timezone/DST/misfire rules and no-overlap execution. Chains/batches can follow once ordinary jobs are complete. Keep existing schema SQL frozen and append application migrations. |
| Tenant access and audit | Record policies/owner predicates exist; memberships, stored roles and durable audit remain recipes | Opt-in tenant context validated against membership; apply it to all queries, relations, caches, files, jobs and streams. Provide role/permission composition without replacing per-record policies. Commit successful audit entries with mutations; separately record denied attempts. Applications own memberships and retention requirements. |
| Production visibility and middleware | JSON logs, IDs, local quotas and explicit OTLP export exist | Automatic HTTP/database/job/outbound spans with W3C context propagation; request/queue/stream/pool metrics and slow-query diagnostics. Add trusted-proxy CIDR rules before accepting forwarded client addresses. Make shared quotas/cache invalidation optional, with explicit outage semantics. Compression must be configurable and preserve prompt SSE flushing. |
| Search and data conveniences | No search integration; ORM escape hatches exist | PostgreSQL full-text search with GIN indexes, authorization predicates, ranking and stable pagination. Add opt-in soft delete/restore/purge conventions and constraint behavior, bounded bulk operations, imports/exports, fixture builders and query-count diagnostics. Keep external search, multi-database routing/sharding and automatic schema diffing deferred. |
| Developer and operator experience | New-app/CRUD CLI, doctor, inspection and custom commands exist | Generators for jobs/events/policies/commands/migrations; one local command for API+worker+scheduler and optional local services. Protected JSON management endpoints and CLI inspection/replay take the place of dashboard work. Versioned event schemas, actual enabled capability metadata and reproducible E2E artifacts improve both human and AI use. |

Spatie explicitly provides relationship includes and field allowlists; those are meaningful gaps beyond Bracel's existing filters. Laravel's validation shows the breadth of nested/conditional request rules worth supporting. [Spatie includes](https://spatie.be/docs/laravel-query-builder/v7/features/including-relationships), [Spatie fields](https://spatie.be/index.php/docs/laravel-query-builder/v7/features/selecting-fields), [Laravel validation](https://laravel.com/docs/13.x/validation).

The notification recommendation follows Laravel's separate mail/database/broadcast channels. Rails' attachment lifecycle illustrates the missing layer above an object store. Typed queues, calendar scheduling and overlap policies should build on Bracel's current workers. [Laravel notifications](https://laravel.com/docs/13.x/notifications), [Active Storage](https://guides.rubyonrails.org/active_storage_overview.html), [Laravel queues](https://github.com/laravel/docs/blob/13.x/queues.md), [Laravel schedules](https://github.com/laravel/docs/blob/13.x/scheduling.md).

OIDC discovery publishes provider metadata and key locations; adopting it does not turn Bracel into an authorization server. If-Match is specifically useful for preventing lost updates; a failed If-Match precondition is 412 rather than a generic 409. PostgreSQL provides a search implementation without another service. [OIDC discovery](https://openid.net/specs/openid-connect-discovery-1_0.html), [HTTP conditional requests](https://www.rfc-editor.org/rfc/rfc9110.html#name-if-match), [PostgreSQL search](https://www.postgresql.org/docs/current/textsearch.html).

## Module ownership

Keep the [accepted library/starter split](../adr/0003-bracel-framework.md). Deep modules should hide repetitive delivery, validation and protocol mechanics behind a small typed interface. Applications still own domain operations and policies, state construction, route registration, migration history and process startup.

- Extend `crates/bracel` for request contracts, queries, idempotency, auth context and shared event/job interfaces.
- Add feature-gated modules initially for durable events, realtime, notifications and webhooks. Split into a dedicated crate such as `bracel-realtime` only when dependency or lifecycle separation earns it; avoid a crate per helper.
- Keep provider implementations in `crates/bracel-integrations`; preserve Axum and SeaORM escape hatches.
- Put runnable examples, application-owned migrations/configuration and E2E scenarios in `starter`; extend editable CLI templates alongside public interfaces.
- Use explicit registration rather than a reflection container or hidden model callbacks. Shared contracts need not force every domain into a universal Resource trait.

Keep Data/Page/Problem for regular HTTP responses. SSE and sockets use a versioned event envelope with event ID, type and data; pre-stream failures use Problem, while failures after headers need documented event/close behavior. OpenAPI describes subscription entry points; separate versioned message schemas document stream contents. File and streaming responses should not be buffered into a JSON envelope.

## Delivery sequence

1. Correct inspection/docs drift; expand validation, PATCH/query conventions, mutation idempotency and concurrency contracts. Specify failure cases and produce one E2E API scenario.
2. Add typed events/transactional publication, credential-lifetime context and replayable SSE. Prove restart, reconnect, two replicas and revoked access before calling it reliable realtime.
3. Build queued notifications, file lifecycle and signed webhooks on the delivery foundation. Extend typed jobs/calendar scheduling as needed by those scenarios.
4. Add WebSockets, production metrics/propagation and optional tenant/audit/search modules. Then address distributed cache/quotas and advanced job orchestration when workload evidence requires them.

Testing, telemetry and documentation accompany every step; step 4 is deeper observability, not permission to defer basic diagnostics. This sequence is a product recommendation, not a release commitment.

## Evidence and AI usability

For each addition, specify failure cases before implementation and prefer process-level E2E scenarios: actual HTTP server, PostgreSQL, worker and relevant local provider. Emit a repeatable artifact containing a manifest (revision plus dirty-patch hash, dependency/service versions, commands and seed), redacted HTTP/event transcripts, assertions, and JUnit/JSON results. Capture evidence from the run, not handwritten success statements. Keep credentials/private payloads out of artifacts.

The strongest first scenario is: authorized create -> commit mutation and event -> stream to the correct owner -> disconnect/reconnect and replay -> deliver queued notification. Verify rollback emits nothing, another owner sees nothing, a failed delivery retries, a slow reader stays bounded, and process restart retains replayable events. A separate raw token stream should prove cancellation and bounded buffering; don't write every AI token to PostgreSQL by default.

There is existing evidence tooling drift: [tooling.rs](../../starter/src/tooling.rs) hardcodes email as recipe_only and identity as bearer_jwt, despite optional mail and machine tokens being implemented. [Data](../../starter/docs/features/data.md) and [performance](../../starter/docs/features/performance.md) retain earlier recipe statements that conflict with newer implementation notes. Generate a capability manifest distinguishing supported, compiled-in, configured and externally verified states. This is an immediate improvement for AI consumers; do not add an AI provider SDK merely to make the framework AI-friendly.

## Deliberately outside the present scope

Web page templates, frontend bundling, rendered forms, rich-text editors, admin/job dashboards, static asset pipelines and page-oriented sitemaps/redirect systems. For operator workflows use authorized JSON endpoints and CLI commands. Billing, incoming email, GIS, GraphQL/gRPC, feature flags and advanced SSO remain later optional modules. PostgreSQL remains the recommended database; broad database compatibility would expand every durable-infrastructure verification obligation.

Only source/document inspection and official-source research were performed for this report. No feature implementation, runtime tests, dependency/version changes, pushes or releases were performed.
